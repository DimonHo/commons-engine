# 公地引擎治理细则

*本文档是公地引擎双层治理的操作手册：公共层社区如何运作，运营层合作社如何治理。配合 [CHARTER.md](../CHARTER.md) 使用。*

---

## 第一部分：公共层社区治理

### 1. 角色与晋升

| 角色 | 定义 | 权利 |
|------|------|------|
| 贡献者（Contributor） | 任何提交过被采纳的贡献（代码/文档/设计/研究）的人 | 参与 RFC 讨论、社区投票 |
| 维护者（Maintainer） | 对某模块有持续贡献，经现有维护者提名+社区认可 | 对应模块的代码合并权 |
| 技术委员会（Tech Board） | 各模块首席维护者组成，选举产生，任期 2 年 | 跨模块架构决策、技术冲突仲裁 |

**晋升流程**：
1. 被提名人持续活跃（过去 6 个月内有有效贡献）。
2. 一名现有维护者提名。
3. 社区讨论期 14 天，无实质性反对。
4. 提名生效。

### 2. 活跃贡献者定义

用于社区投票的"活跃贡献者"资格：
- 过去 12 个月内，有至少 5 次被采纳的贡献（合并的 PR / 被接受的 RFC / 被采纳的文档修订）。
- 或经技术委员会认定为持续贡献者。

活跃贡献者名单由社区维护，每季度更新。

### 3. 决策流程

#### 3.1 日常技术决策（PR 合并）
- 由对应模块的任意一名维护者审批。
- 涉及公共 API 变更或架构影响的，需 2 名维护者审批。

#### 3.2 重大技术决策（RFC）
- 在 `docs/rfcs/` 创建 RFC 文档。
- 讨论期至少 14 天。
- 相关模块维护者投票，简单多数通过。
- 涉及跨模块的，由技术委员会决议。

#### 3.3 社区治理决策（章程修改、战略合作等）
- GitHub Discussions 公开提案，讨论至少 30 天（章程修改 45 天）。
- 活跃贡献者投票，简单多数通过（章程修改 2/3 多数）。
- 公示 14 天（章程修改 30 天）后生效。
- 基金会确认不违反不可篡改底线。

### 4. 冲突处理

- 技术冲突：先在模块维护者间协商；协商不成由技术委员会裁决。
- 社区冲突：由社区选举的调解小组处理（3 人，随机抽取，任期 6 个月）。
- 价值观冲突（涉及不可篡改底线）：基金会介入，行使否决权或指导权。

## 第二部分：运营层合作社治理

### 5. 多利益相关方合作社模型

公地引擎推荐的合作社治理模型——多方合作社（Multi-Stakeholder Cooperative）：

```
┌─────────────────────────────────────────┐
│           合作社全体大会                  │
│   （最高权力机构，年度召开）              │
└───────────────┬─────────────────────────┘
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
┌────────┐ ┌────────┐ ┌────────┐
│劳动者   │ │ 用户   │ │社区/   │
│理事会   │ │理事会  │ │公共    │
│(40%)   │ │(30%)   │ │理事会  │
│        │ │        │ │(30%)   │
└────────┘ └────────┘ └────────┘
    │           │           │
    └─────┬─────┘     ┌─────┘
          ▼           ▼
   ┌──────────────────────┐
   │   理事会（董事会）     │
   │  日常治理与决策        │
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │   运营团队             │
   │  （含技术、地推、客服） │
   └──────────────────────┘
```

#### 三类成员的投票权重

| 成员类别 | 投票权 | 定义 |
|----------|--------|------|
| 劳动者 | 40% | 实际在平台提供服务的骑手/司机/家政工等 |
| 用户 | 30% | 实际使用平台服务的消费者 |
| 社区/公共 | 30% | 地方政府代表、社区组织、独立公益理事 |

> 权重为推荐起点。各地合作社可根据实际情况微调，但劳动者投票权不得低于 33%。

### 6. 利润分配规则

合作社的利润（扣除运营成本和公积金后）按以下原则分配：

| 分配去向 | 比例（建议） | 说明 |
|----------|-------------|------|
| 劳动者分红 | ≥ 60% | 按劳动贡献（单量/时长/评价）分配，非按资本 |
| 公积金 | 15-20% | 用于合作社发展储备、设备购置、风险准备金 |
| 用户回馈 | 5-10% | 降低服务价格或返还用户 |
| 社区贡献 | 5% | 本地社区公益、行业协会 |
| 公地回馈 | ≤ 5% | 回馈公地引擎公共层社区（自愿） |

> 关键原则：利润按劳动分配，不按资本分配。劳动者入股仅作为身份象征（象征性份额），不作为分红依据。

### 7. 算法治理

合作社对基于公地引擎运行的算法拥有配置权和知情权：

1. **参数配置权**：派单规则、定价参数、抽成比例由合作社理事会决定，而非由引擎开发者决定。
2. **算法知情权**：劳动者有权了解影响自己的算法逻辑（"为什么这个单派给我""我的评分怎么算的"）。
3. **算法审计权**：合作社理事会或劳动者代表有权定期审计算法运行结果，检查是否存在系统性偏差（如对某类劳动者的歧视性派单）。
4. **反榨取约束**：合作社不得配置出系统性压低工资、诱导超时劳动的算法参数。

### 8. 入社与退社

**劳动者入社**：
- 完成行业准入要求（如资质证书）。
- 认购象征性合作社份额（金额由各合作社自定，通常为月收入的 1-3 倍，可从收入中分期扣除）。
- 经简单资格审查后成为合作社成员。

**劳动者退社**：
- 任何时候可申请退社。
- 退还象征性份额（扣除已分配的分红）。
- 信用记录可携带。

### 9. 透明度要求

使用公地引擎的合作社须定期公开：

| 项目 | 频率 | 公开对象 |
|------|------|----------|
| 财务收支表 | 季度 | 全体成员 |
| 抽成比例及流向 | 实时 | 全体成员 + 消费者 |
| 派单算法参数 | 实时 | 全体成员 |
| 纠纷仲裁统计 | 季度 | 全体成员 |
| 劳动者收入分布 | 季度（脱敏） | 全体成员 |

### 10. 跨合作社联邦

多合作社之间的协作机制：

1. **信用互通**：劳动者从一个合作社转到另一个合作社时，信用记录可携带（数据格式标准化）。
2. **标准协商**：成立合作社联邦理事会，协调行业标准（服务标准、安全规范、数据接口）。
3. **知识共享**：运营经验、教训、最佳实践在联邦内共享。
4. **联合采购**：多个合作社联合采购基础设施（服务器、保险、设备），压低成本。

## 附录：参考案例

- **The Drivers Cooperative（纽约）**：司机拥有的网约车合作社，已实际运营。
- **Stocksy United（加拿大）**：摄影师合作社图库，盈利且成员分红。
- **Fairmonzo（德国）**：二手物品合作社平台。
- **Mondragon Corporation（西班牙）**：全球最大的工人合作社联邦，10 万+成员。
- **Up & Go（纽约）**：家政工合作社清洁服务平台。

这些案例证明：合作社不是空想，是在真实市场中活着的、盈利的、为劳动者服务的商业模式。
