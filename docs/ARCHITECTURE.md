# 公地引擎技术架构

*本文档定义公地引擎的技术设计：模块划分、技术选型、架构原则和实现路线。*

---

## 一、设计原则

### 1.1 公地优先（Commons First）

公地引擎的每一行代码都属于公共公地（commons）。技术选型应优先考虑：开源、可移植、可 fork、低锁定。不允许引入只能服务于单一商业实体的专有依赖。

### 1.2 渐进式联邦（Progressive Federation）

全国只有一个劳动者 App、一个消费者 App、一个统一后端——用户体验与美团/滴滴完全一样。但随着规模增长，后端可逐步拆分为区域节点（华北、华南、华东……），App 保持统一，用户无感。

- **起步阶段**：单一中心化部署，快速验证单位经济模型。
- **规模化后**：按区域拆分数据库与算力，降低单点故障风险与合规压力。
- **始终不变**：治理权属于全体成员，而非任何单一资本实体。

### 1.3 算法透明（Transparent Algorithms）

所有影响劳动者生计的算法——派单、定价、抽成、评价——必须可解释、可审计。算法逻辑的开源是底线，运行参数应由合作社自己配置，而非由引擎开发者黑箱决定。

### 1.4 AI 原生（AI-Native）

公地引擎从第一天起就以 AI 压缩运营成本为核心策略。客服、审核、调度、地推的边际成本通过 AI 压到极低——这是合作社能在成本上和资本平台竞争的基础。

### 1.5 隐私与数据主权（Data Sovereignty）

劳动者的个人数据归劳动者所有，不归任何资本股东。平台收集的隐私数据（手机号、位置、身份信息）仅用于服务运行，不得出售或用于剥削性目的。随着区域节点拆分，各节点只存储本区域的数据，跨区域数据流动须经治理批准。

## 三、核心模块设计

### 3.1 匹配引擎（Matching Engine）

**职责**：将需求（乘客叫车、用户点餐）与供给（司机、骑手）进行匹配。

**设计要点**：
- 匹配算法可配置：平台按区域配置匹配规则（距离优先、公平轮转、新人保护等），公地引擎不硬编码。
- 算法透明：匹配的决策依据对劳动者可见（"为什么派给我这个单"），可审计。
- 反榨取约束：引擎内置约束参数，防止设计出系统性压低工资的派单黑箱。

**技术方向**：基于地理空间索引（PostGIS / Redis GEO）的实时匹配，事件驱动架构。

> **当前实现**：阶段1 采用 bounding-box 矩形过滤 + 应用层 Haversine 距离计算的两级方案（日均单量 < ~500 足够）。真正的 PostGIS `ST_DWithin` + `geography` + GiST 索引落地见 Issue #44。Redis GEO 未启动。

### 3.2 支付分账（Payment & Settlement）

**职责**：处理交易资金的收取、分账和结算。

**设计要点**：
- 透明分账规则：抽成比例、流向在交易时对劳动者和消费者完全可见。
- 可配置分账：分账规则（多少归劳动者、多少归运营成本、多少归公积金）由全体大会制定，公开透明。
- 多支付通道：适配不同地区的支付基础设施（微信支付、支付宝、银行转账等），通过适配器模式接入。
- 账目可审计：所有资金流向记录在不可篡改的账本中，全体成员有权查阅。

**技术方向**：支付适配器层 + 事件溯源（Event Sourcing）账本。优先接入合规的开源/开放支付接口。

### 3.3 信用评价（Credit & Rating）

**职责**：记录劳动者和用户的信用，用于匹配参考和纠纷依据。

**设计要点**：
- 双向评价：劳动者评价用户，用户评价劳动者——打破单向权力。
- 反惩罚性设计：评价不直接挂钩劳动者的接单资格（防止平台用评价系统惩罚劳动者），仅作为参考。
- 数据归个人：劳动者的评价数据可携带（劳动者离开这个合作社时可以带走自己的信用记录）。

### 3.4 纠纷仲裁（Dispute Resolution）

**职责**：处理劳动者与用户、劳动者与合作社之间的纠纷。

**设计要点**：
- AI 初筛 + 人工仲裁：AI 做初步分类和证据整理，复杂纠纷由平台仲裁委员会处理。
- 透明流程：仲裁规则公开，劳动者有权申诉、有权知道仲裁结果的理由。
- 仲裁委员会由劳动者代表、用户代表和社区代表组成（比例见治理细则）。

### 3.5 调度引擎（Dispatch Engine）

**职责**：在匹配完成后，协调劳动者的行动路径和时间安排。

**设计要点**：
- 路径优化服务于劳动者效率，而非平台抽成最大化。
- 劳动者可设定自己的工作偏好和边界（不想接的时段、区域、单型），引擎尊重这些设定。
- 多模式调度：支持打车（实时 + 预约）、外卖（多取多送）、家政（预约制）等不同调度模式。

### 3.6 治理模块（Governance Module）

**职责**：支撑合作社的民主治理——投票、议事、分红、透明账目。

**子模块**：
- **投票系统**：支持多利益相关方加权投票（劳动者 / 用户 / 社区各有权重）。
- **议事平台**：提案、讨论、表决的线上流程。
- **分红计算**：按劳动贡献计算利润分配。
- **透明账目**：平台的收支、抽成流向对全体成员公开。

### 3.7 会员与身份系统（Identity & Membership）

**职责**：管理劳动者、用户、合作社成员的身份和权限。

**设计要点**：
- 劳动者身份验证（行业准入要求，如网约车驾驶员证）。
- 合作社成员管理（入社、退社、股权/份额记录）。
- 隐私保护：身份验证信息加密存储，仅用于服务运行，不得出售或用于剥削性目的。

### 3.8 AI 服务层（AI Services Layer）

**职责**：为所有模块提供 AI 能力，压低运营成本。

**子能力**：
- 智能客服：自动处理常见咨询，复杂问题转人工。
- 内容审核：自动审核商家信息、用户评价中的违规内容。
- 调度优化：基于实时数据的路径和供需优化建议。
- 文档处理：自动化合规文档、法务文档的生成和审查。
- 语音/多语言：适配多地区劳动者的语言需求。

**技术方向**：支持接入本地部署的开源模型（数据主权优先）+ 按需的云端大模型 API。模型层抽象，不锁定单一供应商。

## 四、技术选型

### 4.1 核心原则：混合架构

公地引擎采用**核心业务 + AI 服务**分离的混合架构：

- **核心业务层**（匹配/分账/评价/仲裁/治理/会员）使用 **Spring Boot 4.x + Kotlin**——强类型、高性能、金融级可靠。
- **AI 服务层**（智能客服/内容审核/调度优化/文档处理）使用 **Python** 独立部署——充分利用 Python AI 生态。

两层通过 HTTP/gRPC 通信，各自独立演进。

### 4.2 技术栈

| 层 | 选型 | 理由 | 实现状态 |
|----|------|------|---------|
| 后端语言 | **Kotlin**（JDK 21+）| 简洁、类型安全、协程与虚拟线程并行 | ✅ |
| 后端框架 | **Spring Boot 4.x** | 企业级成熟度、模块化单体天然支持、GraalVM 原生镜像 | ✅ MVP |
| 数据库 | PostgreSQL + PostGIS | 地理空间、关系数据、成熟开源 | ✅ PostgreSQL（PostGIS ⏳ 待落地） |
| 缓存 | Redis | 实时位置、匹配队列 | 📋 未启动 |
| 消息队列 | NATS / Redis Streams | 事件驱动、轻量 | 📋 未启动 |
| 前端 | React Native（移动端）| 跨平台，劳动者 App + 消费者 App | 📋 未启动 |
| | React（管理后台）| | 📋 未启动 |
| AI 服务层 | **Python**（独立微服务）| AI/ML 生态最完善，模型推理、NLP、数据处理 | ⏳ 骨架（1/3 模块） |
| 原生编译 | GraalVM Native Image | 启动快、内存省，降低部署成本 | 📋 未启动 |
| 部署 | Docker + docker-compose（起步）→ K8s 多区域（规模化后） | 单一中心化起步，渐进式区域拆分 | ✅ docker-compose |
| CI/CD | GitHub Actions | 开源友好 | ✅ |
| 构建工具 | Gradle (Kotlin DSL) | Kotlin 原生支持、DSL 灵活 | ✅ |

### 4.3 为什么选 Spring Boot 4.x + Kotlin

1. **性能**：JDK 21 虚拟线程（Project Loom）让匹配引擎这类高并发 I/O 场景性能极佳，无需异步框架复杂度。
2. **类型安全**：Kotlin 强类型 + 空安全，支付分账等金额逻辑更可靠，运行时错误更少。
3. **金融/支付行业标准**：Java/Kotlin 是金融领域事实标准，支付分账模块生态成熟。
4. **模块化单体**：Spring DI 天然支持模块化单体架构，模块边界清晰，未来拆分微服务无缝。
5. **GraalVM 原生镜像**：启动时间毫秒级，内存占用极低，符合"低成本运营"理念。
6. **开发效率**：Kotlin 简洁度接近 Python，配合 AI 编程工具（Copilot/Cursor），开发效率不输动态语言。
7. **Spring Boot 4.x 新特性**：虚拟线程一等支持、更好的可观测性、更轻量的运行时。

> 注：技术选型可由社区技术委员会通过 RFC 流程讨论修订。

## 五、部署模型

### 5.1 全国单一平台（起步阶段）

全国统一部署一套后端服务：
- 一个劳动者 App、一个消费者 App、一个统一后端。
- 用户无感跨城使用——App 自动定位到当前城市，订单路由到中心服务。
- 多云灾备：主从热备，异地容灾，避免单点故障导致全国瘫痪。

用户体验与美团/滴滴完全一致：一个 App 覆盖全国，劳动者的身份、信用、收入跨城市连续。

### 5.2 渐进式区域节点（规模化后）

当单量增长到单一中心难以承载（或合规要求区域隔离）时，按区域拆分后端节点：

```
          全国统一的 App（劳动者端 + 消费者端）
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
    华北节点     华东节点    华南节点  ...
   (京津冀鲁)   (江浙沪皖)   (粤桂琼)
         │          │          │
         └──────────┼──────────┘
                    ▼
           全局协调层（治理、标准、联邦议事）
```

- **App 不变**：用户始终只有一个 App，区域拆分对用户完全透明。
- **数据隔离**：各区域节点只存储本区域用户数据，满足属地合规。
- **治理统一**：区域节点是技术和数据层面的拆分，治理权仍属于全体成员（全体大会 + 理事会）。
- **弹性扩展**：新区域按需新增节点，不影响已有节点运行。

### 5.3 数据主权

- 用户隐私数据（手机号、位置、身份信息）仅用于服务运行，不得出售或用于剥削性目的。
- 规模化后各区域节点只存储本区域数据，跨区域数据流动须经治理批准。
- 脱敏的运营指标（单量、响应时间等）用于改进服务，须经治理批准后使用。

## 六、实现路线

### 阶段 1：MVP（3-9 个月）

优先实现五个核心模块的最小可用版本：
1. 匹配引擎（单一模式：如先做实时打车匹配）
2. 支付分账（单一支付通道）
3. 信用评价（双向评分）
4. 纠纷仲裁（AI 初筛 + 简单人工流程）
5. 治理模块（基础投票 + 透明账目）

产出：一个可以在测试环境跑通完整流程的实例，和一个部署文档。

### 阶段 2：试点运营（9-18 个月）

- 在一个城市/区域跑通真实单量，验证无补贴下的单位经济模型。
- 补充：调度引擎、会员系统、AI 服务层的核心能力。
- 产出：可验证的公开运营数据。

### 阶段 3：全国扩展与区域联邦（18 个月+）

- 从单一城市扩展到全国，App 保持统一。
- 按区域拆分后端节点（华北、华东、华南……），用户无感。
- 多模式支持（打车、外卖、家政等）。
