## 一、命题与设计原则

### 1.1 存在性命题

公地引擎阶段 2 的核心命题是：

> **在劳动者到手 ≥ 80% 的前提下，平台仅靠 ≤ 15% 的运营抽成，能否覆盖全部运营成本，实现无补贴单位经济为正？**

这是整个项目的**商业可行性验证**。若命题不成立，则「劳动者合作社平台」模式无以为继；若成立，则证明资本抽成不是平台存在的必要条件。

### 1.2 设计原则

1. **可复算**：所有公式、参数、假设显式列出，任何人可代入不同城市参数复算。
2. **城市参数化**：模型以「城市」为可替换参数容器，首城未定稿时先用成都假设（对接 [#47 选址报告](./city-selection.md)），定稿后替换为精确基准。
3. **映射代码现实**：分账结构严格对应当前 `SettlementRule`（`backend/payment/.../domain/Model.kt`），不发明代码里不存在的资金流。
4. **双视角**：同时回答「平台能否盈亏平衡」和「劳动者能否体面谋生」——两者必须同时为正，缺一不可。
5. **不代决治理参数**：抽成比例、公积金比例、利润分配规则的最终值由全体大会决定。本模型用**建议区间**做敏感性分析。

## 二、资金流模型（映射代码）

### 2.1 单笔订单资金拆分

消费者每笔支付总金额 `AO`（Average Order value），按当前代码 `SettlementRule.DEFAULT` 拆为三份：

```
消费者支付 AO（¥）
  ├── 劳动者所得     = AO × 0.80   （workerShareRate）
  ├── 平台运营费     = AO × 0.15   （platformOperationRate）← 平台的"收入"
  └── 公积金         = AO × 0.05   （commonsFundRate）
```

**代码约束**（已实现，不可违背）：
- 三份之和 = 100%（`SettlementRule.init` 校验）
- 劳动者所得 ≥ 70%（反榨取底线，`require(workerShareRate >= 0.70)`）
- 平台抽成上限 15%（RFC-001 `maxPlatformFeeRate = 0.15`，**需全体大会最终确定**）

> **关键界定**：本模型中「平台收入」= `AO × platformOperationRate`。这是平台可用于覆盖自身成本的唯一资金来源。公积金（5%）属于合作社成员的公共储备，**不是平台收入**，不可挪用。

### 2.2 与竞品的结构性差异

| 维度 | 资本平台（美团/滴滴） | 公地引擎 |
|------|----------------------|----------|
| 名义抽成 | 15–25%（消费者侧） | ≤ 15%（代码硬约束） |
| 劳动者实际到手 | 约 60–70%（含隐性扣减） | ≥ 80%（透明分账，无隐性） |
| 利润归属 | 股东 | 劳动者分红 ≥60% + 公积金 |
| 抽成透明度 | 黑箱 | 每笔交易实时公开（章程 §4.3） |

**公地引擎的单位经济命题之所以重要**：它要求平台在**更低的抽成（≤15%）和更高的劳动者分成（≥80%）**下，依然能盈亏平衡。这比资本平台的单位经济约束更紧——若成立，证明「抽成不是因为需要，而是因为能」。

## 三、平台单位经济模型

### 3.1 符号定义

| 符号 | 含义 | 单位 |
|------|------|------|
| `AO` | 单均订单金额（消费者支付） | ¥/单 |
| `r_platform` | 平台运营抽成比例 | 0.15（建议值，≤0.15 硬约束） |
| `R_order` | 单均平台收入 = AO × r_platform | ¥/单 |
| `VC_order` | 单均可变成本 | ¥/单 |
| `CM_order` | 单均边际贡献 = R_order − VC_order | ¥/单 |
| `FC_month` | 月固定成本 | ¥/月 |
| `Q_day` | 日均订单量 | 单/日 |
| `Q_BE_day` | 日均盈亏平衡订单量 | 单/日 |

### 3.2 核心公式

**单均边际贡献：**

```
CM_order = R_order − VC_order
         = AO × r_platform − VC_order
```

**日均盈亏平衡订单量：**

```
Q_BE_day = FC_month / (CM_order × 30)
```

**判定**：当 `Q_day ≥ Q_BE_day` 时，平台单位经济为正（无补贴可持续）。

### 3.3 单均可变成本 `VC_order` 拆解

| 成本项 | 计算方式 | 行业基准 | 假设值（成都配送） |
|--------|----------|----------|---------------------|
| 支付通道费 | AO × 0.38–0.6% | 微信/支付宝商户费率 0.38–0.6% | AO × 0.6% |
| 云计算分摊 | 固定/单 | 约 ¥0.02–0.05/交易 | ¥0.03 |
| 短信/通知 | ¥0.04/条 × 2–3 条 | 验证码+状态通知 | ¥0.10 |
| 客服分摊 | 月客服成本 / 月单量 | 取决于单量 | ¥0.20（初期单量低时偏高） |
| **VC_order 合计** | | | **≈ AO × 0.6% + ¥0.33** |

> **诚实标注**：客服分摊在低单量阶段（< 500 单/日）会显著拉高 VC，因为客服人力有最低刚性。这会在敏感性分析中体现——它正是冷启动期单位经济最难看的原因。

### 3.4 月固定成本 `FC_month` 拆解（最小试点配置）

| 成本项 | 假设值（成都/月） | 说明 | 决策属性 |
|--------|-------------------|------|----------|
| 云基础设施 | ¥1,500 | PostgreSQL/Redis/NATS + 应用实例（按需规模） | 可计算 |
| 核心团队（技术） | ¥0（志愿期）→ ¥15,000 | 阶段2 初期依赖开源志愿；过渡期 1 名兼职工程师 | **需人类决定**人力配置 |
| 地推/社区运营 | ¥3,000 | 1 名兼职社区运营，种子劳动者招募 | **需人类决定** |
| 办公/合规杂项 | ¥1,500 | 注册地址、基础行政 | 视法人结构 |
| **FC_month 合计（志愿期）** | **¥6,000** | 最小可行配置 | |
| **FC_month 合计（含1兼职技术）** | **¥21,000** | 过渡期配置 | |

> **关键假设**：志愿期 FC = ¥6,000/月 是「最小可行试点」假设。是否接受志愿期、何时转入有薪团队属**需人类维护者/核心小组决定**。

## 四、情景测算（成都假设，城市参数化）

> 以下使用成都即时配送场景的假设基准。参数来自公开行业报告二次研究（与 [#47](./city-selection.md) 数据来源一致），**非实测**。首城定稿后替换为精确值。

### 4.1 输入参数

| 参数 | 值 | 来源/说明 |
|------|----|-----------|
| AO（单均订单金额） | ¥22 | 成都即时配送均值（2024 行业报告） |
| r_platform | 0.15 | 建议值，代码硬约束上限 |
| VC_order | ¥22×0.6% + ¥0.33 = ¥0.46 | 见 §3.3 |
| FC_month（志愿期） | ¥6,000 | 见 §3.4 最小配置 |
| FC_month（含兼职技术） | ¥21,000 | 过渡期 |

### 4.2 计算

```
R_order = 22 × 0.15 = ¥3.30
CM_order = 3.30 − 0.46 = ¥2.84

【志愿期】Q_BE_day = 6000 / (2.84 × 30) ≈ 70 单/日
【含兼职技术】Q_BE_day = 21000 / (2.84 × 30) ≈ 247 单/日
```

### 4.3 判读

- **志愿期**：日均 **70 单**即可覆盖平台运营成本。这个量级一个中型社区配送就能达到，**命题成立的可能性很高**。
- **含1名兼职技术**：日均 **247 单**。相当于约 30–40 名活跃骑手（按人均 6–8 单/日计），冷启动 1–2 个月内可达。
- **结论（初步）**：在成都配送场景、80/15/5 分账结构下，无补贴单位经济为正**是可实现的**。但此结论对 FC 敏感——每增加 ¥10,000/月 固定成本，平衡单量增加约 117 单/日。

## 五、劳动者生计视角（必须同时为正）

单位经济为正不仅指平台盈亏平衡，还必须验证**劳动者靠 80% 分成能否体面谋生**。

### 5.1 劳动者单均收入

```
单均劳动者所得 = AO × workerShareRate = 22 × 0.80 = ¥17.60
```

### 5.2 劳动者时薪测算

| 假设 | 单/小时 | 时薪 | 对比基准 |
|------|---------|------|----------|
| 低效（新人/淡季） | 1.5 | ¥26.4 | 成都最低时薪 ¥22（2024） |
| 正常 | 2.5 | ¥44.0 | 美团骑手实测约 ¥25–35 |
| 高效（熟练/旺季） | 3.5 | ¥61.6 | — |

### 5.3 判读

- 即便低效期（1.5 单/小时），劳动者时薪 ¥26.4 仍高于成都最低时薪基准。
- 正常效率下（2.5 单/小时），时薪 ¥44 显著优于竞品骑手实测水平——**这正是公地引擎的核心价值主张：更高分成 → 更高时薪 → 更体面劳动**。
- **前置条件**：单量必须足够支撑 2+ 单/小时的接单密度，否则劳动者「等单成本」会侵蚀收入。这与 [#49 种子供需](https://github.com/DimonHo/commons-engine/issues/49) 的临界规模直接相关。

> **诚实标注**：以上未计入劳动者自付成本（电动车/电池/通信/保险）。竞品骑手的自付成本约占收入 10–15%。若计入，公地引擎劳动者净收入仍优于竞品（因为分成更高），但模型应纳入此项做完整测算——列入本文件 v0.2 改进项。

## 六、敏感性分析

### 6.1 盈亏平衡单量对固定成本的敏感度

| FC_month（¥/月） | Q_BE_day（单/日） | 含义 |
|-------------------|-------------------|------|
| 6,000（纯志愿） | 70 | 最小试点 |
| 12,000 | 141 | +1 兼职运营 |
| 21,000 | 247 | +1 兼职技术 |
| 30,000 | 352 | +1 全职技术 |
| 50,000 | 587 | 小团队配置 |

**结论**：固定成本是单位经济的最大杠杆。阶段 2 应**尽可能延长志愿期 + 延迟雇佣**，把 FC 控制在最低水平，使盈亏平衡单量保持在 100–200 单/日的可达区间。

### 6.2 盈亏平衡单量对 AO（单均金额）的敏感度

（固定 FC = ¥12,000/月，r_platform = 0.15）

| AO（¥） | R_order | VC_order | CM_order | Q_BE_day |
|---------|---------|----------|----------|----------|
| 15（低价配送） | 2.25 | 0.42 | 1.83 | 219 |
| 22（基准） | 3.30 | 0.46 | 2.84 | 141 |
| 30（中高价） | 4.50 | 0.51 | 3.99 | 100 |
| 40（网约车短途） | 6.00 | 0.57 | 5.43 | 74 |

**结论**：品类选择对单位经济影响巨大。**网约车（AO 更高）的单位经济天然优于配送**。但配送冷启动门槛更低（资质/车辆要求低）。这解释了 [#47](./city-selection.md) 为何将「配送优先（长沙）」作为备选策略——用低门槛品类跑通模型，再扩展高 AO 品类。

### 6.3 抽成比例影响（治理参数，仅做敏感性，不代决）

| r_platform | 劳动者所得 | 平台 Q_BE_day（FC=12000, AO=22, VC=0.46） | 治理属性 |
|------------|-----------|---------------------------------------------|----------|
| 0.10（10%） | 0.85 | CM=1.74 → Q_BE=230 单/日 | 全体大会可调（≤15%） |
| 0.15（基准） | 0.80 | CM=2.84 → Q_BE=141 单/日 | 建议值 |
| 0.20（如果放开） | 0.75 | CM=3.94 → Q_BE=102 单/日 | **违反 RFC-001 上限**，不建议 |

> **决策边界**：抽成比例最终值**需全体大会决定**。本表仅展示不同选择对平衡单量的影响，帮助决策者理解 trade-off，不提供推荐。

## 七、验证路径（如何证伪这个模型）

单位经济模型的价值在于**可被真实数据证伪**。验证路径：

| 阶段 | 动作 | 验证什么 | 前置依赖 |
|------|------|----------|----------|
| 桌面（当前） | 本模型 | 公式自洽、假设合理 | — |
| 预试点 | 用竞品公开单量数据代入 | AO/VC 假设是否合理 | #47 定稿 |
| 冷启动 | 跑真实订单，采集 AO/VC/FC 实测值 | 模型参数是否准确 | 种子供需启动 |
| 稳态 | 连续 30 天 Q_day vs Q_BE_day | 单位经济是否真正为正 | 临界规模达成 |

**证伪条件**：若连续 30 天实测 `Q_day < Q_BE_day` 且无下降趋势，则「无补贴正单位经济」命题在该城市/品类下不成立，需调整参数（降 FC、提 AO、换品类）或承认模式不可行。**诚实面对这一可能**。

## 八、城市参数化结构

为支持首城定稿后快速切换，本模型的城市参数封装为以下结构（未来可脚本化复算）：

```yaml
# config/pilot/city-params.yml（规划中，非现有文件）
city: chengdu  # ← 首城定稿后替换
scenario: delivery  # delivery | ride-hailing | mixed
unit_economics:
  AO: 22.0              # 单均金额 ¥（城市×品类基准）
  r_platform: 0.15      # 平台抽成（≤0.15 硬约束，全体大会定终值）
  worker_share: 0.80    # 劳动者所得
  commons_fund: 0.05    # 公积金
variable_cost:
  payment_fee_rate: 0.006   # 支付通道费率
  cloud_per_order: 0.03     # 云计算分摊
  sms_per_order: 0.10       # 通知
  support_per_order: 0.20   # 客服分摊（单量低时偏高）
fixed_cost_monthly:
  infra: 1500
  tech_team: 0          # 志愿期=0，过渡期按实际填
  field_ops: 3000
  admin: 1500
```

切换城市时，修改 `city` + `AO` + `fixed_cost_monthly` 即可复算全部结果。

## 十一、结论（初步，待实证）

1. **命题初步成立**：在成都配送场景、80/15/5 分账、最小志愿期配置（FC≈¥6,000/月）下，日均 70 单即可盈亏平衡。这个量级在单一社区配送场景可达。
2. **最大风险是固定成本**：每 ¥10,000/月 FC 增加约 117 单/日 平衡单量。阶段 2 应严控 FC。
3. **核心价值主张成立**：劳动者 80% 分成下，正常效率时薪 ¥44，显著优于竞品——这是公地引擎最硬的差异化。
4. **品类选择是杠杆**：网约车（高 AO）单位经济天然优于配送，但配送冷启动门槛更低。建议配送切入、逐步扩展。
5. **须实证证伪**：以上均为桌面测算，须用真实订单数据验证。若连续 30 天 Q_day < Q_BE_day，须诚实承认并调整。
