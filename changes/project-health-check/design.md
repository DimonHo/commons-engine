# Design: 项目健康检查整改清单

## Context

公地引擎阶段1 完成后，项目积累了两类系统性问题：
1. **文档与代码脱节**——文档声明的技术选型在代码中不存在，开发指南停留在阶段0
2. **流程空转**——设计了 PR 审查流程但实际代码直推 main，设计了 RFC 流程但唯一的 RFC 还是草案

当前项目仅 1 名人类维护者 + AI Agent 团队，所有 AI 可做的规划工作已触达边界。继续产出新规划文档的边际价值为零。

## Goals

1. **一份可信的整改清单**——每项问题有位置、严重度、根因、建议，可直接作为后续修复任务的输入
2. **立即可执行的修复**——detekt/JaCoCo 提交（DEBT-2）可在本变更中直接完成
3. **停止无效产出**——通过校准 AI Agent 角色，停止规划层的重复劳动

## Decisions

### D1: 文档标注策略——「诚实标注」而非「删除」

**选择**: 在 ARCHITECTURE.md 中保留所有技术选型描述，但逐项标注实现状态（✅ 已实现 / ⏳ 计划中 / 📋 未启动）。

**理由**: 删除会让读者不知道未来方向；保留但不标注会让读者误以为已实现。诚实标注同时服务两个目的。

**替代方案**: 将未实现的选型全部移到「路线图」章节——**否决**，因为会打乱架构文档的完整性（读者需要知道某层最终长什么样）。

### D2: 技术债在本变更中只标注不修复

**选择**: SHELL-1（4 模块落库）、DEBT-1（PostGIS）、DEBT-3（AntiExploitation 补全）标注为技术债，不在本变更修复。

**理由**: 本变更是「健康检查」不是「治疗」。修复 4 模块落库是阶段2 工程任务，应在独立的 change 中完成。混在一起会让变更过大、无法验收。

**例外**: DEBT-2（detekt/JaCoCo）作为「直接修复」纳入，因为工作区已有现成代码，只差提交验证。

### D3: AI Agent 校准方向——从规划转向工程辅助

**选择**: 暂停总工程师 Agent 的规划草案 cron job，重新定义为工程辅助角色。

**理由**: 3 份规划草案（选址/经济/冷启动）已充分覆盖阶段2 战略层。后续的价值在于「把规划变成代码」，而非继续产出规划。

**替代方案**: 维持现状让 Agent 继续产出——**否决**，日报已连续 4 天标注「触达边界」，继续产出浪费 token。

## Risks And Trade-Offs

| 风险 | 缓解 |
|------|------|
| 整改清单产出后无人执行（和 Agent 一样触达边界） | 下一变更 `phase2-engineering-blueprint` 会将 🔴 项转化为工程任务 |
| detekt CLI 方案可能在新 Kotlin 版本下再次不兼容 | 已在 build.gradle.kts 注释中记录兼容性问题和替代路径 |
| Agent 角色调整可能遗漏有用的日报产出 | 技术 Agent 日报保留，只调整总工程师 Agent 的规划产出频率 |
