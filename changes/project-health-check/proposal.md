# Proposal: 项目健康检查整改清单

## Why

公地引擎已完成阶段1 MVP（8 模块、49 个 Kotlin 文件、端到端测试绿灯），但在向阶段2 推进时暴露出系统性的文档-代码脱节、流程空缺和技术债积累。具体问题包括：架构文档声明的核心选型（API 网关、消息队列、GraalVM）在代码中完全不存在；CONTRIBUTING.md 仍停留在阶段0 描述（说用 pytest，实际是 Gradle）；RFC-001 标注草案但代码已实现；4 个模块未落库；AI 服务层 3 个模块中 2 个完全空壳。这些问题如果不先清理，阶段2 的工程工作将建立在模糊的地基上。

## What Changes

产出一份**结构化整改清单**（本文档 + specs/），逐项诊断以下 5 个维度的问题，标注严重度、根因和整改建议：

1. **文档与代码矛盾** — 架构图/README/CONTRIBUTING 声称的东西在代码中不存在或已过时
2. **空壳与未实现** — 目录存在但无实质代码的模块
3. **技术债** — 已知但未排序的代码层面欠账（持久化缺失、PostGIS 未真正使用、detekt/覆盖率未恢复）
4. **流程缺口** — 分支保护、代码审查、RFC 审批等流程空转或未启动
5. **文档自身矛盾** — 文档之间的不一致（如 README 路线图 vs ARCHITECTURE 实现路线）

## Scope

### In
- 逐项列出所有已发现的问题，每项含：位置、严重度（🔴 阻塞 / 🟡 重要 / 🟢 改进）、根因、整改建议
- 对每项给出建议处理时机（立即 / 阶段2 启动前 / 阶段2 中）
- 对技术债项给出依赖关系和优先级排序
- 更新或标注需要修正的文档清单

### Out
- 不编写新功能代码
- 不修改治理参数（抽成比例等需全体大会决定）
-不做阶段2 工程任务拆解（那是下一个变更 `phase2-engineering-blueprint` 的工作）
- 不评估战略层面合理性（选址/经济模型等已由各自文档充分标注决策边界）

## Impact

| 影响面 | 说明 |
|--------|------|
| 文档可信度 | 整改后文档与代码一致，新贡献者不会被误导 |
| 阶段2 前置条件 | 技术债排序后，可明确哪些必须在阶段2 启动前清理 |
| 开发流程 | 流程缺口暴露后，可决定是否在阶段2 引入分支保护/代码审查 |
| AI Agent 团队 | 校准 Agent 的工作范围——停止在已触达边界的规划层继续产出 |

## Capabilities

- **documentation-consistency**: 文档与代码的一致性校验和修正
- **tech-debt-triage**: 技术债的识别、排序和整改计划
- **process-audit**: 开发流程的缺口诊断和建议
